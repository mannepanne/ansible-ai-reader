# Security Response Headers

How Ansible sets HTTP security headers, where each one lives, and why. These headers are what scanners like [securityheaders.com](https://securityheaders.com) grade.

## Why two locations

Ansible runs as an OpenNext worker on Cloudflare. A response is generated by the worker, then Cloudflare's edge can add or override headers on the way out. **The edge wins.** That split determines where each header belongs:

| Header | Set in | Reason |
|---|---|---|
| `Strict-Transport-Security` | **Cloudflare edge** (exact source unconfirmed — see below) | Cloudflare injects HSTS at the edge. Setting it in the worker too would be shadowed or duplicated. |
| `X-Frame-Options` | Worker (`src/middleware.ts`) | Not edge-injected — the worker owns it. |
| `X-Content-Type-Options` | Worker (`src/middleware.ts`) | Same. |
| `Referrer-Policy` | Worker (`src/middleware.ts`) | Same. |
| `Permissions-Policy` | Worker (`src/middleware.ts`) | Same. |
| `Content-Security-Policy` | Worker (planned) | See [CSP spec](../../SPECIFICATIONS/12-content-security-policy.md). Not yet enforced. |
| (removed) `X-Powered-By` | `next.config.ts` (`poweredByHeader: false`) | Suppresses Next.js information disclosure. |

## Worker headers (`src/middleware.ts`)

The middleware applies a fixed `SECURITY_HEADERS` map to every page it serves, via `applySecurityHeaders()`. HSTS is deliberately absent here (the edge owns it). Covered by `src/middleware.test.ts`.

## HSTS — Cloudflare dashboard

HSTS is **not** in this repo (confirmed: no `strict-transport` match in source). It is injected **somewhere at the Cloudflare edge** for the `hultberg.org` zone — the exact source is unconfirmed.

> **Verify the source before changing it.** The live value is `max-age=2592000` (30 days). Cloudflare's SSL/TLS → Edge Certificates → HSTS feature only offers 6 months / 1 year / 2 years, so 30 days strongly suggests the header comes from a **Transform Rule (Rules → Transform Rules → Modify Response Header)** or the zone settings API (`GET /zones/{id}/settings/security_header`) rather than the HSTS dashboard page. Check those first; otherwise enabling the SSL/TLS HSTS feature could create a *second* source and the duplicate/override this worker was designed to avoid.

- `max-age` should be at least 6 months (`15768000`); 1 year (`31536000`) is the recommended value.
- `includeSubDomains` on.
- `preload` is a **one-way door**: enabling it commits the entire `hultberg.org` tree (all subdomains) to browsers' hardcoded HTTPS list and requires submission to [hstspreload.org](https://hstspreload.org). Do not enable without explicit sign-off.

## Verifying

The only meaningful local test is against the **built** worker, not `next dev` (which honours config the deployed worker can drop):

```bash
npm run build:worker
npx wrangler dev --port 8787 --local   # in one terminal
curl -sI http://localhost:8787/ | grep -iE 'x-frame|content-type-options|referrer|permissions'
```

After deploy, the authoritative check is a fresh scan at securityheaders.com (HSTS only shows there, since it is edge-injected and absent from the local worker).
