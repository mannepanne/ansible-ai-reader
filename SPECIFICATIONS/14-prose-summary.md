# 14 — Prose summary: a second summary type built for reading

**Status:** Draft, awaiting `/review-spec`
**Last updated:** 2026-09-06
**Depends on:** nothing. Consumed by [13-fika-reading-habit.md](./13-fika-reading-habit.md) and shares its style machinery with [relay/restraint-and-prose-tuning.md](./relay/restraint-and-prose-tuning.md)

---

## Problem

The current summary is bullet points from Perplexity. That is right for scanning and wrong for reading. It is repetitive, it has no voice, and the pleasure of reading something is gone. If Fika is going to be a moment you look forward to over coffee, the thing in the email has to read like a piece, not a checklist.

Two constraints make this harder than "ask for prose":

1. It has to be **bounded**. A summary you can read in a known number of minutes, every time.
2. It has to **not sound generated**. Not "avoid AI tells" as a prompt line, which does nothing, but a written style guide, a deterministic checker, and a rewrite loop.

## Goals

- A second summary per item, `prose_summary`, alongside the existing bullets. The bullets stay unchanged and stay on Perplexity.
- Generated by the Claude API. Perplexity is a search model and is kept for what it is good at.
- Hard reading-time bound, default 3 minutes.
- A shared plain-prose style guide and tells checker that the Relay narrator adopts too.
- Readable in the web card (a "Read" tab next to "Scan"), in the Fika email, and later as the script for audio.

## Non-goals

- Replacing the bullet summary. Both exist.
- Opinion, commentary, or the Commentariat feature. The prose summary carries the author's argument, not the model's.
- Perfect tells detection. The checker catches the known patterns and the rewrite loop fixes what it catches. Novel tells are found by reading and added to the list.

## Design

### 1. What a prose summary is

A short piece of plain writing that tells you what the article says, in the order the argument is made, so that when you finish you could explain it to someone else. It answers "what is this and what does it claim" in the first two sentences, carries the argument in three to six paragraphs, and stops when the argument stops.

It is not a review, not a reaction, not a "why this matters to you" and not an essay with a finisher. If the article is a list, the prose still reads as prose. If the article is thin, the summary is short. The word budget is a ceiling, not a target.

### 2. Word budget

- Setting `prose_reading_minutes`, integer 1 to 10, default 3. At 220 words per minute that is a ceiling of `minutes × 220` words, so 660 for the default.
- The ceiling is passed into the prompt and enforced after generation. Over 110 percent of the ceiling triggers one rewrite pass with the instruction "shorten to under N words, cutting whole points before trimming sentences". Still over after that: store it anyway and set a lint flag. Never block.
- The web card shows "3 min" next to the Read tab, computed from the actual word count.

### 3. Model and request shape

- Model: `claude-opus-5`, held in one config constant so it can be swapped or A/B tested. Fable 5.1 is the stronger writer and roughly twice the price; try it in the eval (section 8) before committing.
- Thinking: adaptive (the default, so omit the parameter). Effort `medium` to start; the eval decides whether `high` earns its cost on this task. Anthropic's Fable 5.1 guidance warns that at `xhigh` and `max` the model drafts the whole piece in its reasoning and then again as output, which doubles cost for no gain on prose.
- `max_tokens` 4000. Non-streaming is fine at this size.
- Include the server-side refusal fallback the SDK docs recommend for Opus 5 class models, so a safety refusal on an unusual article degrades to a fallback model rather than a missing summary.
- Input: the same article content the Perplexity job fetches. No 30k truncation: the context window makes it unnecessary and the conclusion is where arguments land. Cap at 150k characters for cost; log when hit.
- Cost estimate at Opus 5 rates: a 3000-token article in, 900 tokens out including thinking, about $0.04 per summary. At 30 items a week, about $1.20 a week. Fable 5.1 doubles that.

### 4. Prompt structure

System prompt, in this order, cached with `cache_control` on the stable blocks:

1. **Role and job**, five lines. "You are writing a short summary of an article for one reader who will read it over coffee. Tell them what it says, in its own order, so they could explain it to someone else."
2. **The style guide** (section 5), loaded from `prose-style/plain-prose.md` at build time, the same way Relay assembles its persona from `relay-agent/*.md`.
3. **One complete example**: an article excerpt, a correct summary, and a one-sentence rationale. Anthropic's Fable 5.1 guidance is specific that a single full example with a rationale is what stops the model from lifting source passages unmarked. The example must show one short quoted phrase in quotation marks and everything else reworded.
4. **Format rules**: no headings, no lists, no bold, no title, no sign-off. Paragraph breaks every three to five sentences. Quote at most one short phrase from the source and mark it.

User message: title, author, source, the word ceiling, then the content. The ceiling goes in the user message because it changes per user and would break the cache in the system prompt.

### 5. The style guide, `prose-style/plain-prose.md`

This file is the single source of truth for both the prose summary and the Relay narrator's craft. Relay's existing `relay-agent/ansible-agent-craft-and-cadence.md` already carries a "tells to cut" list; the shared file absorbs those and the material below, and the craft doc references it rather than duplicating.

**Part A: the anti-pattern, defined.** Anthropic's own paragraph, used verbatim because it defines the thing rather than naming it:

> Mannered prose substitutes metaphor and flourish for direct statement. Instead of "a parameter worth varying," the mannered writer produces "a dial worth turning." Instead of "this point still matters," they write "this point earns its keep." The phrases exist to display the writer, not to convey the idea, and readers can tell. That is why mannered prose irritates: it makes the reader work harder so the writer can perform. It is also imprecise. Metaphors drag in connotations the writer did not choose and cannot control. The fix is to say what you mean. When a literal phrase is available, use it.

**Part B: the named tells.** Each pattern gets a name, a description, and one example as it came out of a draft, then how it should have read. The seed list comes from a marked-up draft, reproduced here as the source material:

> *The ROI on most conferences is a lanyard and 40 new connections who never reply.*
> Marked: **"Classic Claude setup."** The wry one-line thesis with a specific-sounding number pulled from nowhere.
>
> *The invoice is $3,000 and a full week of founder attention.*
> Marked: **"Generic listing of costs, pulled from thin air."** Invented precision.
>
> *The ticket is $800. Flights and hotel push the trip past $3,000. Add travel days, the recovery day, the inbox you ignored, and the real cost is a week of the scarcest resource your company has.*
> Marked: **"Typical rhetorical phrasing"** on "the inbox you ignored" and "the real cost". The escalating list that ends in an abstraction.
>
> *What comes home: a badge, two "great to meet you" emails, and a photo of a keynote slide you will never open again.*
> Marked: rhetorical phrasing again. The colon-then-triad of deflating specifics.
>
> *No stage. No badge. Nothing to post a selfie with. It just compounds, quietly, while the hallway conversations evaporate by Tuesday.*
> Marked: **"Classic 'No X. No Y. Just Z.' phrasing"** and **"The dead giveaway, LLMs' favourite word: quietly."**
>
> *Conferences are a fine place to make friends. They are a terrible line item to file under marketing. Go for the people. Stop booking it as pipeline.*
> Marked: **"Classic two-sentence juxtaposition finisher."**

From that and from Relay's existing list, the named patterns the guide forbids:

| Name | Pattern | Detectable? |
|---|---|---|
| The wry setup | Opening with a one-line thesis joke and a made-up number | Partly (number in first sentence without a source) |
| Invented precision | Specific figures not present in the source | Yes: numbers in output absent from input |
| The escalating list | Comma list climbing to an abstraction ("the real cost is...") | Partly (`the real X is`) |
| The colon triad | "What comes home: a, b, and c" deflating specifics | Partly (colon followed by exactly three items) |
| No X. No Y. Just Z. | Fragment triad negations | Yes, regex |
| Quietly, and its family | quietly, simply, merely, just compounds, earns its keep, does the work, here's the thing, the real cost, at its core, in short, dial worth turning | Yes, word list |
| It's not X, it's Y | The contrast reframe as default cadence | Yes, regex, allow once |
| The juxtaposition finisher | Ending on two short contrasting sentences | Yes: last paragraph is two sentences under 12 words with a contrast word |
| The announced turn | "And here is where it stops being..." | Partly, phrase list |
| The sentence about its own sentence | Commenting on the line just written | Phrase list ("which is a sentence that") |
| Epoch labelling | "This is the move of the age" | Phrase list |
| Uniform rhythm | Every sentence 14 to 20 words | Yes: standard deviation of sentence length below a threshold |
| Unmarked lifting | Source passages reproduced without quotation marks | Yes: longest common substring with source over 12 words and not inside quotes |

**Part C: what to do instead.** Plain by default. Vary sentence length. Name the real thing. When the source has a number, use it; when it does not, do not invent one. End when the argument ends.

The guide is a living file. Every tell found by reading is added with its example. That is the editorial loop, and it is cheap.

### 6. The tells checker, `src/lib/prose/tells.ts`

A pure function `checkTells(text, source) → Finding[]`, each finding with a pattern name, the offending text, and a severity of `hard` or `soft`.

- **Hard**: invented precision, No-X-No-Y triad, unmarked lifting, over the word ceiling by more than 10 percent, any heading or list markup.
- **Soft**: word-list hits, the contrast reframe more than once, the juxtaposition finisher, uniform rhythm.

Flow after generation:

1. Run the checker.
2. Any hard finding, or three or more soft findings: one rewrite request quoting each finding verbatim with the instruction to fix those and change nothing else.
3. Run the checker again. Store the result regardless. Save the findings that remain in `prose_lint_flags` (jsonb) so they are visible in the admin dashboard and we can see which patterns the model keeps reaching for.
4. Never loop more than once. Never block storage.

The checker is shared with Relay: the piece-review capture from Stage 2.2a can run it over drafts and record findings alongside the human review.

### 7. Generation trigger

Lazy, not pipeline. Reasons: cost lands only on items that get read, and the pipeline latency stays as it is.

- A new job type `prose_generation` on the existing queue consumer, dispatching like `tags_generation` does.
- Enqueued by: the Fika cron when it builds a batch (for any batch item without a prose summary), and by a "Read as prose" action on the web card. The Fika batch is built before send time so the prose exists when the email goes out; if the job has not completed, the email falls back to bullets for that item and says nothing about it.
- Idempotent per item. Regeneration is an explicit action, like summary refresh.
- Alternative considered: generate for every synced item in the pipeline. Rejected for now; revisit if lazy generation makes the Fika email routinely fall back to bullets.

### 8. Evaluation before rollout

A small blind eval, run once before enabling in Fika:

- 12 articles already in the database, spread across sources and lengths.
- Generate prose with Opus 5 at `medium`, Opus 5 at `high`, and Fable 5.1 at `medium`.
- Blind read: for each article, the three summaries in random order plus the existing bullets. Rate readability 1 to 5, and mark any sentence that sounds generated.
- Run the checker over all outputs and compare its findings with the marked sentences. A pattern the reader marks that the checker misses goes into the guide and the checker.
- Decide the model and effort from the ratings, and the cost from the usage fields on the responses.

The claude-api skill's `build-eval` flow is the right tool if this grows beyond a one-off.

### 9. Data model

```sql
ALTER TABLE reader_items
  ADD COLUMN prose_summary text,
  ADD COLUMN prose_summary_model text,
  ADD COLUMN prose_summary_words integer,
  ADD COLUMN prose_lint_flags jsonb,
  ADD COLUMN prose_generated_at timestamptz;

ALTER TYPE job_type_enum ADD VALUE IF NOT EXISTS 'prose_generation';

ALTER TABLE users
  ADD COLUMN prose_reading_minutes integer NOT NULL DEFAULT 3
    CHECK (prose_reading_minutes BETWEEN 1 AND 10);
```

Token usage is recorded on `sync_log` the way Perplexity tokens are, with a separate counter so costs are attributable.

### 11. Acceptance criteria

- [ ] `checkTells` detects every "Yes" row in the table with unit tests per pattern, including at least one true negative per pattern.
- [ ] A summary over 110 percent of the ceiling triggers exactly one rewrite and is stored either way.
- [ ] Unmarked lifting of 12 or more consecutive source words is caught; a quoted phrase is not.
- [ ] Generation is idempotent per item; regeneration is explicit.
- [ ] The Fika email uses prose when present and bullets otherwise, with no visible difference in layout.
- [ ] The Read tab shows the computed reading time.
- [ ] The eval in section 8 has been run and its outcome recorded in this spec before Fika defaults to prose.
- [ ] Tests first, coverage targets hold, `npx tsc --noEmit` clean.
- [ ] REFERENCE docs: new `features/prose-summary.md`, `ai-summaries.md` cross-reference, `database-schema.md`.

### 12. Four risks

- **Value.** The bet is that a three-minute plain piece is something you want to read and a bullet list is not. The blind eval tests that directly before anything ships to the email.
- **Usability.** Two tabs on a card is fine. The risk is the fallback: if prose is often missing at send time, Fika feels inconsistent. Build the batch early enough that generation finishes.
- **Feasibility.** New dependency on the Anthropic SDK in the Workers runtime; the SDK supports fetch-based runtimes. The checker is regex and string work. The rewrite loop is one extra call.
- **Viability.** Roughly a dollar a week at current volume. Lazy generation keeps it proportional to reading, not saving.

### 13. Open questions for review

1. Should the custom `summary_prompt` from Settings apply to prose too? (Position: no. It was written for bullets and would fight the style guide. A separate optional "what I care about" line could come later.)
2. Is 220 words per minute the right reading speed for the ceiling, or should the setting be words directly? (Position: minutes, because that is how a person thinks about coffee.)
3. Does the Commentariat analysis ever belong in the prose? (Position: no. Different job.)
4. Run the checker as a hard gate on Relay pieces too, or advisory only? (Position: advisory in the review capture first; see the Relay tuning note.)

### 14. Rollout

1. Style guide, checker, and tests. No API calls yet. This alone is useful to Relay.
2. Generation path with the SDK behind the `prose_generation` job type. Web card tab. Owner only.
3. Run the eval. Record model, effort, and cost decision here.
4. Fika switches to prose-first.
